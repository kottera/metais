# ADR-010 — W7-C8: the go command a test runs keeps the host's C toolchain

**2026-10-20, PLAN-2026-10-metais-v1 W7-C8.** W7-C4 gave every go command a
test runs `testenv.GoEnv`'s whole environment, which took `CC` and `PATH`
from the host and nothing else of the C toolchain. On the linux/amd64
dispatch image, `internal/conformance`'s `TestMain` then failed building
`./cmd/metais` under `-race`:
`zig-cc-shim (cc): refused: CC_TOOLCHAIN_TARGET_GLIBC is not set`.

**The mechanism.**

- **Why `-race` reaches the C compiler.** On linux the race runtime needs
  cgo, so a `-race` build compiles `runtime/cgo` with `CC`, in the go
  command's environment. On darwin it does not: the race runtime there is
  cgo-free, so the darwin runner never runs `CC` for a race build of
  `metais` and never showed the defect.
- **Why the compiler refused.** The host's `CC` is the cc toolchain's
  zig-cc shim. It takes its target only from `CC_TOOLCHAIN_TARGET_GLIBC`
  and `CC_TOOLCHAIN_TARGET_MACOS`, never from the build host, and refuses
  without them. It also reads `SDKROOT` and `DEVELOPER_DIR`. `GoEnv`
  passed none of them.
- **Who is exposed.** A go command a test runs through `GoEnv` reaches
  `CC` only when it builds with `CGO_ENABLED=1` and its closure has C:
  `internal/conformance`'s race build of the tool, on linux. Two other
  callers set `CGO_ENABLED=1` without compiling C: `internal/pkgtree`'s
  closure listing, which compiles nothing, and `internal/tools/release`'s
  tampered rebuild, whose closure has no C. The rest build with
  `CGO_ENABLED=0`. All of them take the same environment, so a test that
  later compiles C takes the fix too.

Pinned false first: `TestGoCommandKeepsHostCToolchain` sets `CC` to a fake
compiler that refuses unless `CC_TOOLCHAIN_TARGET_FAKE` is set, and
otherwise runs the host's own. It builds a cgo program, whose C no build
cache holds, in `GoEnv`'s environment. Against the old `GoEnv` it failed on
darwin with `# runtime/cgo` and `fakecc: refused:
CC_TOOLCHAIN_TARGET_FAKE is not set`. With the fix it passes, and the fake
is seen to have run.

**What landed.** `GoHost.CC` becomes `GoHost.CToolchain`, the host's C
toolchain as `KEY=VALUE`, and `GoEnv` appends it. The rule: GoEnv keeps the
configuration that decides how C compiles on this host, and nothing that
decides which Go code, modules or Go flags a build takes. That is two sets:

- **The go command's configuration of the C toolchain**, as the host's
  `go env` resolves it, a `GOENV` file included: `CC`, `CXX`,
  `CGO_CFLAGS`, `CGO_CPPFLAGS`, `CGO_CXXFLAGS` and `CGO_LDFLAGS`.
- **The compiler's own variables**, which it reads from its environment
  rather than from the go command: `CC_TOOLCHAIN_*` (the cc toolchain's
  shim), `ZIG_*` (the zig it runs) and `SDKROOT` and `DEVELOPER_DIR`
  (Apple's xcrun, by which `/usr/bin/cc` and the shim find the SDK).

Every other variable of the host is still dropped. A compiler that needs
one outside this set is added to the rule by name, with its documentation.
`GoEnv`'s own variables cannot be overridden by it: no name in either set
is one `GoEnv` sets, and `CGO_ENABLED` stays the caller's.
