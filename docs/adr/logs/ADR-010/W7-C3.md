# ADR-010 — W7-C3: inspect lists a package's examples in name order, and the map ranges that reach output

**2026-10-20, PLAN-2026-10-metais-v1 W7-C3.** D4 item 2 makes the same
inputs give the same bytes on every run. `inspect --json` did not, for a
package with more than one example. The scoped gate on a macOS host, the
first to grant `internal/hostfs`' `TestPresentationUnderTerminal` a pty,
saw two documents of `aut/test-containers` differ in the order of
`result.examples` and in the first-example step of `next`.

**The mechanism.** `examplesOf` returns the examples as a Go map, by name.
`inspectOutcome` built the `examples` list by ranging over that map, so
the list took Go's randomized map iteration order on every run and on
every platform. ADR-008 D6 item 8 already orders the examples by name, and
`inputOf`, beside it, iterated `sortedKeys(examples)`. The list now
iterates `sortedKeys` too, so the examples are in name order by code
point, and `next`'s `metais ls <package> examples/<first example>/ -r`
names the first of them.

**Why nothing caught it.** Every sandbox denies the pty slave, so the one
test that ran `inspect` twice over a package with several examples and
compared the documents byte for byte had only ever skipped. The tests that
compare `inspect` documents without a terminal
(`TestInspectSourceAndPacked`, `TestReadingPackedAndSourceAgree`) inspect
packages with at most one example. The others compare only codes and exit
statuses, or decode the inputs. `internal/cli`'s
`TestInspectExamplesInNameOrder` now inspects the seven-example package 32
times and holds the list to name order with no terminal. It was red before
the fix.

**The sweep.** Every `range` over a Go map in the module's non-test code
was found by type, not by name: 49 sites. Every `maps.Keys`, `maps.Values`
and `maps.All` call already passes straight to `slices.Sorted`.

- **Fixed:** `internal/cli/inspect.go`'s examples, above, and
  `internal/pkgtree/pkgtreetest`'s `Check`. `Check` reported a List that
  left out several wanted entries in map order, which reached only a test's
  failure text. It now reports them in byte order, under
  `TestCheckReportsMissingInByteOrder`.
- **Map order on purpose, under a fault only:** `internal/author/pack.go`'s
  `mapOrdered` (`fault.PackMapOrder`), and `internal/liquid`'s
  `unorderedMembers` (`fault.MapOrder` through `Env.UnorderedObjects`,
  Amendment A2). Each is the planted fault a determinism detector must
  see, and no zero-fault run reaches it.
- **Harmless:** every other site does one of these:
  - sorts what it collects before use;
  - writes each key's own slot of another map or slice;
  - only counts, tests membership or takes a maximum;
  - hands the members to `value.NewObject`, which sorts them.

  `internal/cli`'s `fill` replaces the placeholders of a next step in map
  order, which would matter if a substituted value could hold another
  placeholder's text. It cannot: each value is a number or an entry path,
  and an entry path refuses `<` and `>` (`internal/unitext`, the
  `package.name.character` rule).

**No conformance vector.** ADR-011 D8 defines no `inspect` operation, and
D8 item 3 makes the reading commands a property of ADR-008's command line,
not an operation. So the order is held by the tool's tests, not by the
suite.
