# ADR-010 — W5b-2: the hostfs open-file-limit tests' cost, and StageNew_abort's timeout

**2026-10-19, PLAN-2026-10-metais-v1 W5b-2.** D14 item 7 and D11 item 3: the cost of
`TestShapesWriteTheirLimitUnderTheOpenFileLimit` and
`TestExistingWritesItsLimitUnderTheOpenFileLimit`, and whether
`TestShapesWriteTheirLimitUnderTheOpenFileLimit/StageNew_abort` hangs.
Measured on darwin/arm64 with go1.26.9, under `-race`, CPU time by
`getrusage`.

## StageNew_abort was slow, not hung

W5-1's run on `main` reached the 600 s package timeout in this subtest,
with its goroutine in a syscall. The mechanism is a package that is slow on
a shared host, not a call that blocks:

- **Nothing on the path can block on another party.** Every call the
  subtest makes is local file-system metadata work on entries the test
  itself created: `openat`, `fstatat`, `mkdirat`, `write`, `fstat`, `close`
  and `unlinkat`, on local APFS. No FIFO is opened (and every open for
  reading carries `O_NONBLOCK`), no lock is taken, and no network file
  system is involved.
- **One instrumented run timed every call.** Of 300,100 calls (100,000
  `MkdirAll`, 100,000 `Create`, and the 100,100 removals of `Abort`), the
  slowest took 0.29 s, and none took more than 1 s. The time is spread
  evenly across the calls.
- **The wall time is mostly kernel time, and it swings.** Alone, the
  subtest took 46 s, 97 s and 116 s of wall time; the two runs measured
  took 35 s and 40 s of CPU time, nine tenths of it system time. The package's two 100,000-file tests together took 65 s to
  326 s of wall time, and 60 s to 131 s of CPU time, across six runs. User
  time swings with system time, so the host's scheduling moves the CPU time
  as well as the wall time.
- **It is where the clock runs out.** The package runs
  `TestExistingWritesItsLimitUnderTheOpenFileLimit` eighth and
  `TestShapesWriteTheirLimitUnderTheOpenFileLimit` forty-fourth.
  `StageNew_abort` is the latter's last subtest, so it is the package's
  last 100,000-file workload and its longest subtest. A package that takes
  237 s alone and 355 s in a full gate passes 600 s inside it on a busier
  host.
- **The dump matches.** A deliberate 20 s `-timeout` on the subtest alone,
  which was making progress, prints its goroutine as `[syscall]`, in
  `(*Writer).Create`'s `close`. The runtime resets a goroutine's wait time
  on every return from a syscall (`exitsyscall`), so a single call blocked
  for minutes would print as `[syscall, N minutes]`.

No defect, so there is nothing to fix and no pin. The 600 s bound belongs
to the gate's oversubscription of the host, which the wave's shared-host
cap addresses.

## Their cost cannot fall much without proving less

Each subtest's CPU time was split by stage in one run:

| Subtest | Product work at the default count | Removal of what it committed | Test's own |
|---|---|---|---|
| `Shapes/StageNew`, 100,000 | write 15.5 s | cleanup 5.5 s | count 0.8 s |
| `Shapes/StageNew_abort`, 100,000 | write 23.1 s, `Abort` 16.9 s | none (`Abort` removes it) | inside the write |
| `Existing/commit=true`, 100,000 | check, write, commit 21.3 s | cleanup 5.4 s | seed 0.5 s, `tree` 2.0 s |

The tests owned two pieces of work, and now drop them:

- `StageNew_abort` called `MkdirAll` before every file, 99,900 times more
  than its commit sibling. A `MkdirAll` of an existing directory creates
  and records nothing, so the `Output` that `Abort` ends is the same.
- `Existing` built and sorted every name of its tree to count the files
  (`countFiles` counts them), and listed the seeded tree before the write
  even when only the abort compares it.

In one process, back to back, the 99,900 calls cost 0.94 to 1.03 s, and
counting by `tree` cost 2.2 to 2.9 s against 1.0 to 1.2 s for
`countFiles`. That is about 2 to 3 s of CPU time per run. Whole-run totals
cannot resolve it: across three alternating pairs they were 59.8, 131.4
and 124.7 s before, and 129.6, 112.6 and 105.3 s after.

What remains is the property's own work. It writes ADR-009 D3's default
counts through each shape, under an open-file soft limit of 128 that R1-015
forbids lowering. Each file costs a handful of system calls through `os.Root`: a `Lstat`
of its directory, the exclusive open, a `Stat`, the write and the close. The
committed output must then go, because the test's directories are
temporary (D14 item 1). The race detector does not drive the cost. It
inflates user time, and user time is about a tenth of the total: without
it, `StageNew_abort` still took 29.7 s of CPU time. Cutting deeper would
mean fewer entries, which proves the bound at less than the limit, or
fewer calls per entry, which changes the tool.
