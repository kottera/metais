# ADR-006 — W5b-3: one edit per new finding code

**2026-10-19, PLAN-2026-10-metais-v1 W5b-3.** A2 landed. The registry's
table is split by family: each family's entries, and the constants other
packages name its codes by, are in `internal/finding/registry_<family>.go`,
and `registry.go` joins them with the JSON Schema keyword codes of
`schemacodes.go`. `TestRegistryFamilies` holds the layout: a family's
file holds only that family's codes, in code order, and the table is
exactly the family files and the keyword codes.

`spec/findings/registry.json` is generated from the table by
`go generate ./internal/finding` (`TestGenerateRegistry`), and
`TestRegistryFileGenerated` fails when the committed file, or the copy
`internal/specdata` embeds, differs from it by a byte. The first
regeneration moved the `items` member of two parameters
(`manifest.input.form_shape`'s `types`, `report.step_skipped`'s `steps`)
to where every other parameter writes it, after `type`. Nothing else in
the file changed, and the catalog and `spec/statements.json` regenerate
byte-identical.

`TestEmittedCodes`, which compared the table with a hand-kept copy of
every code, is gone. It held a second copy of the table, not a fact about
emission. What the module emits is held by `New`, which panics on an
unregistered code, by `TestFindingCodesCovered` and the unwired list, and
by internal/cli's per-refusal tests (ADR-008 D16 item 2).

`internal/finding/testdata/unwired.txt` stays hand-written. The registry
does not hold the wave that is expected to wire a code. A list generated
from "registered and produced by no vector" would also list every new,
unwired code with no one deciding to, which is the decision the list
exists to record.
