# ADR-013 — W2-4: release.yml, its dry run, and the site deployed from the released tag (D7 item 3)

**2026-10-23, PLAN-2026-10-metais-public W2-4.** Publishing is in place,
and nothing is published. `docs/dev/release.md` is the release procedure
and the release act.

- **`release.yml`** (D7 item 3.2 and 3.3) runs on `workflow_dispatch`,
  naming the draft by its tag. Its `release` job runs in the `release`
  environment and runs `.github/scripts/release.sh`'s steps:
  - **prepare** checks the draft and pushes nothing. `go run
    ./internal/tools/release verify` holds the assets to exactly
    `SHA256SUMS` and the archives of `buildline.Shipped`, each with its
    line's SHA-256, and runs the shipped linux/amd64 `metais`, which must
    report the version. prepare checks a `spec-<M>.<m>` the draft names,
    in one `Specification release:` line of its body, against ADR-011 D5
    item 2: an ancestor of the target that holds the released list. A
    prerelease names none. A release that is not a prerelease must
    implement only released revisions (ADR-011 D5 item 6).
  - **push-tags**, **publish** and **push-tap** push the annotated tags,
    publish the draft (a prerelease when the version has a suffix), and
    push the formula W2-3's generator writes to the tap with `TAP_TOKEN`
    (D7 item 5, R-PUB-11). The tap is updated by a prerelease only while
    no release without a suffix exists. The tap's commit follows its
    README: signed off by the dispatching account, with no
    `Co-authored-by` line.
  - No second build, no attestation and no goreleaser (D7 items 1, 2 and
    4). The top-level `permissions` are empty. The release job has
    `contents: write` and `actions: read`, and only push-tap is given
    `TAP_TOKEN`.
- **The dry run.** The `dry_run` input exists for proving the workflow
  alone. It skips the push steps, the publish and the pages job, and
  `release.sh` refuses each push step under it as well. A run that is not
  dry refuses, before it pushes anything, a private repository and a
  `release` environment without a required reviewer, since on GitHub's
  free plan a private repository enforces no reviewer.
- **What deploys the site (D7 item 3.4, ruling R-W2-1).** `release.yml`
  calls `pages.yml` as a reusable workflow, as its last job, once the
  publish step has succeeded, with the released tag. A release published
  with `GITHUB_TOKEN` starts no new workflow run, so a `release:
  published` trigger would not fire, and a token that does would add a
  credential to the `release` environment that this does not need.
  `pages.yml` has no push or release trigger. Its build checks that the
  tag's release is published before it checks the tag out with its whole
  history, and builds with `site/build.sh --release <version>
  <SHA256SUMS>` from the release's `SHA256SUMS`. Dispatched with a
  published tag, it redeploys that release's site, for an erratum
  (ADR-011 A8 item 1). Its jobs stay gated on a public repository.
- **Tests.** `internal/tools/release`'s `TestReleaseScript` runs
  `release.sh` against a repository, a tap and a stand-in `gh`: a dry run
  that pushes nothing, a prerelease, a release with its specification, a
  prerelease after a release, a re-run after the tags were pushed, and
  each refusal. `TestVerify` holds `verify`. `internal/guarantees`'
  `TestReleaseWorkflow` holds `release.yml`'s shape, and
  `site`'s `TestWorkflow` holds `pages.yml`'s triggers and gate.
- **Not exercised while private:** `pages.yml`'s deploy and the `release`
  environment's required reviewer are first exercised at `v1.0.0-rc.1`
  (Wave 3). The dry run is dispatched by Ed under R-W1-2, against a
  draft, and its run is linked on the pull request.
