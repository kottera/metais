# ADR-009 — W7-C5: Amendment A3's lowered defaults, and the CPU ceiling at two minutes

**2026-10-20, PLAN-2026-10-metais-v1 W7-C5.** This entry implements Amendment
A3 item 3 for the three cases that broke 1 GiB. It lowers `grep-context`,
`output-size`, `output-total` and `schema-work` in D3's table, in
`internal/limits` and, for the limits it states, in chapter 14's §14.6. It
sets the calibration suite's CPU ceiling to 120 s (A3 item 1).
`schema-work`'s default follows the wave orchestrator's ruling R-W7-C5.

The figures were measured in this item's sandbox, which is linux/amd64 on
a shared host: Ubuntu 26.04.1, Linux 7.0.0-38, 12 CPUs. They are a sandbox's
figures, not evidence (plan §5). darwin/arm64, darwin/amd64 and linux/arm64
need a real-host re-run, and so does linux/amd64. The scaling probes ran
the suite's own cases at lowered limits. The `grep-context` and
`output-total` probes used go1.26.2, because the host sets
`GOTOOLCHAIN=local`. The `schema-work` probes and the calibration run used
go1.26.9, the toolchain `go.mod` names.

## How each peak scales

**`grep-context`.** `grep` keeps every line it shows: each match is kept
with its context, and the case's lines are 1,024 bytes as shown. The
command then builds the human rendering, which it builds even under
`--json`, and encodes the JSON document in memory. The peak is about 5 KiB
of resident memory per shown line. The shown lines number
`grep-matches × (2 × grep-context + 1)`:

| `grep-matches` | `grep-context` | Shown lines | Peak |
|---|---|---|---|
| 1,000 | 10 | 21,000 | 124 MiB |
| 1,000 | 20 | 41,000 | 226 MiB |
| 2,000 | 10 | 42,000 | 274 MiB |
| 10,000 | 5 | 110,000 | 620 MiB |
| 10,000 | 6 | 130,000 | 657 to 700 MiB, over three runs |
| 10,000 | 7 | 150,000 | 707 to 738 MiB, over eight runs |
| 10,000 | 8 | 170,000 | 910 to 1,061 MiB, over four runs |
| 10,000 | 100 (the old default) | 2,010,000 | 9,449 to 9,472 MiB (W6-A2) |

The peak varies by up to 15% between runs of the same case, because the
collector's timing varies. `grep-context` goes from 100 to **7**. That is
the largest value that held within 1 GiB on every run: 8 broke it once,
at 1,061 MiB. `grep-matches` stays at 10,000, because a result bound is
what an agent reading `grep`'s JSON relies on, and the per-match context is
a display choice. The suite's two runs at 7 peaked at 688 and 725 MiB.

**`output-total`, with `output-size`.** A render holds every output it
renders until it writes them. Each output is rendered into a buffer that
grows by doubling, so a buffer can hold up to about 2.3 times its output
while it renders. The peak is about `output-total` plus 1.3 times
`output-size`:

| `output-size` | `output-total` | Peak |
|---|---|---|
| 64 MiB | 256 MiB | 462 MiB |
| 64 MiB | 512 MiB | 801 MiB |
| 128 MiB | — (the `output-size` case) | 304 to 305 MiB |
| 128 MiB | 256 MiB | 527 MiB |
| 128 MiB | 384 MiB | 785 MiB |
| 128 MiB | 512 MiB | 913 to 914 MiB, over three runs |
| 256 MiB | — (the `output-size` case) | 597 MiB |
| 256 MiB | 512 MiB | 1,044 to 1,045 MiB, over three runs |
| 256 MiB | 1 GiB (the old defaults) | 1,817 to 1,821 MiB (W6-A2) |

Both limits drive the peak. At the old `output-size` of 256 MiB, no
`output-total` larger than one output stays within 1 GiB. `output-size`
goes from 256 MiB to **128 MiB**, and `output-total` from 1 GiB to
**512 MiB**. The resulting 914 MiB is the same on every run, because its
buffers are large and allocated the same way each time. W6-A2 found the old
case within 0.2% across the four targets. The suite's run at these
defaults peaked at 914 and 915 MiB, and `output-size` alone at 304 MiB.

**`schema-work`.** The case validates an array of `schema-work / 12`
integers, which is exactly the limit's units. What drives its peak is
loading that array, not the units the validation counts. Loading costs
about 480 bytes of resident memory per array element, before any unit is
counted. With `--limit schema-work=1`, which refuses the validation before
it evaluates anything, the case's input of 1,666,666 elements still peaks
at 802 MiB, and half as many at 402 MiB. The heap profile puts the cost in
loading: `jsonx`'s parser, 47%; canonicalization (`jsonx.Canonical`
through `gowebpki/jcs`), 23%; and `inputs.build`, 11%. Evaluation adds
about 10%. The case's array grows with `schema-work`, so its peak does too:

| `schema-work` | Peak |
|---|---|
| 10,000,000 | 550 MiB |
| 12,000,000 | 574 to 645 MiB, over four runs |
| 14,000,000 | 736 to 758 MiB, over five runs |
| 16,000,000 | 719 to 911 MiB, over four runs |
| 18,000,000 | 918 to 1,027 MiB, over two runs |
| 20,000,000 | 887 MiB |
| 100,000,000 (the old default) | 4,511 to 5,074 MiB (W6-A2) |

`schema-work` goes from 100,000,000 to **14,000,000**, and the new default
bounds this case. W6-A2's peaks for the case differ by 12% across the
four targets: darwin/arm64 is highest, at 5,074 MiB, against 4,511 MiB on
linux/amd64. 16,000,000 held within 1 GiB on every run here, but its
911 MiB has no room for that 12%. 14,000,000 at 758 MiB does, and the
suite's run at it peaked at 743 MiB.

Two paths that reach past 1 GiB are not bounded by `schema-work` and not
by this item. They belong to the corrective item **W7-C6**:

- **Input loading.** One input of `[0,0,…]` costs about 240 bytes of
  resident memory per byte at any `schema-work`, so an input at
  `input-size`'s 32 MiB would peak at about 7.5 GiB. `input-size` and
  `inputs-total` are what bound this, and this item does not change them.
- **A failing `anyOf`'s nested findings.** `input.any_of` nests every
  failing alternative's findings beneath it, and the `findings` limit
  counts only the top-level finding, at about 5 KiB per unit. A schema of
  16 levels of a two-branch `anyOf` over `{"type":"string"}`, validating
  `5`, peaked at 1.27 GiB and wrote 100 MB. With 18 levels it peaked at
  4.9 GiB and wrote 415 MB.
