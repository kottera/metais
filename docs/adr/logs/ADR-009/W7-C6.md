# ADR-009 — W7-C6: the two memory paths W7-C5 found, measured, and what bounds each

**2026-10-20, PLAN-2026-10-metais-v1 W7-C6.** W7-C5's root-cause of
Amendment A3's `schema-work` case found two paths that no limit bounds:
loading an input, and the findings a failing `anyOf` nests. This entry
measures each on this item's host and records what the item changed.

The host is darwin/arm64, a sandbox on a host shared with other Work
Orders. Figures are peak resident memory (`ru_maxrss`) and CPU time of
`metais validate --json` as a process, built with `-trimpath` and go1.26.2,
because the host sets `GOTOOLCHAIN=local`. They are a sandbox's figures,
not evidence (plan §5). darwin/amd64, linux/arm64 and linux/amd64 need a
real-host re-run, and so does darwin/arm64. A peak varies by up to about
15% between runs, as the collector's timing varies. "main" is `8a56ce8`;
"C6" is this item's branch.

## Nested findings, and the failing tree beneath them

**The mechanism.** A failing `anyOf` or `oneOf` whose branches are all
rejected is one finding whose `alternatives` list each branch's findings,
recursively, and the `findings` limit counted only the top-level finding.
Before any finding is made, the library returns its failure tree, the
adapter converts it to `schemafail.Failure`s, `inputs` copied it again to
strip the input's name, and the mapping built every finding, nested ones
included, before the report capped anything. The JSON document was then
built in memory whole, more than once.

The cases are a schema of *n* levels of a two-branch `anyOf` over
`{"type":"string"}` (`anyOf n`), or of `allOf` (`allOf n`), each level
reaching the one below by `$ref`, validating `5`. Each costs
4 × 2ⁿ + 1 units of `schema-work`. `allOf` nests no finding: its 2ⁿ
failures are one finding, so it measures the failure tree alone.

| Case | Units | main | C6 | C6, written |
|---|---|---|---|---|
| `anyOf 14` | 65,537 | 291 MiB | 303–309 MiB | 24 MB, every finding listed |
| `anyOf 16` | 262,145 | 1,346–1,474 MiB | 956–1,075 MiB | 77 MB, 100,000 listed |
| `anyOf 17` | 524,289 | 2,748 MiB | 1,729 MiB | 100,000 listed |
| `anyOf 18` | 1,048,577 | 4,265 MiB | 3,333 MiB | 79 MB, 100,000 listed |
| `allOf 14` | 65,537 | 150 MiB | 99–156 MiB | one finding |
| `allOf 16` | 262,145 | 550–589 MiB | 327–424 MiB | one finding |
| `allOf 18` | 1,048,577 | 2,090 MiB | 1,357 MiB | one finding |

What changed, by ADR-006's log entry for W7-C6: the cap counts every
finding listed within alternatives (MTS-FND-020, MTS-FND-021), a choice is
built listing at most the cap, the mapping streams into a de-duplicating
sink, the failure tree is stripped in place, and the JSON document writes
its findings one at a time. The listing is now bounded by `findings`: at
most 100,000 findings in all, the same bound and about the same peak as
the `findings` case.

**The failure tree's cost per unit, cut toward the library's floor.** The
plan orchestrator ruled (2026-10-20, Q7) that `schema-work` is set under
A3 item 3, after the cost of a failing tree is cut as far as it can be
without changing a finding. This item then cut:

- the field lookup (ADR-006 D6 item 9), which walked a failure's whole
  ancestry for each finding and split every pointer on the way: each
  failure's answer is now worked out once, from its parent's, and held
  only along the path being mapped;
- `branchOf` and `Failure.Walk`, which split or copied each failure's
  evaluation path, now compare it as written and share one path buffer;
- a finding's parameters, held as a sorted list rather than a map;
- a branch gathered by `finding.Branch`, which New no longer sorts and
  de-duplicates a second time;
- writing, JSON and human alike, which hands each finding within
  alternatives to the stream as it is encoded, so one finding listing the
  limit's findings is never one buffer.

No finding changes: every case's document is byte-identical before and
after each cut, and the conformance suite passes.

|---|---|---|---|---|
| `anyOf 14` | 65,537 | 291 MiB | 303–309 MiB | 151 MiB |
| `anyOf 16` | 262,145 | 1,346–1,474 MiB | 956–1,075 MiB | 541–575 MiB |
| `anyOf 17` | 524,289 | 2,748 MiB | 1,729 MiB | 1,089 MiB |
| `allOf 16` | 262,145 | 550–589 MiB | 327–424 MiB | 345 MiB |

**What is left grows with the failure tree, and `schema-work` bounds it.**
The library's own `ValidationError` tree for `allOf 16`, measured in a
process that does nothing else, is 30 MiB live: about 120 bytes per unit.
The rest is the adapter's `schemafail.Failure` tree, chiefly each
failure's evaluation path, a string as long as the failure is deep, and
the collector's headroom: about 1.8 KiB of resident memory per unit when
every unit fails. The `schema-work-anyof` case scales as follows on this
host, run three times at each point:

| `schema-work` | Peak |
|---|---|
| 400,000 | 717 to 792 MiB |
| 450,000 | 779 to 820 MiB |
| 500,000 | 847 to 877 MiB |
| 600,000 | 1,226 MiB, one run, before the last two cuts |
| 800,000 | 1,444 MiB; 1,567 MiB before the last two cuts |

**`schema-work` goes from 14,000,000 to 450,000** under A3 item 3: the
largest value whose case peaked at most 80% of 1 GiB on this host, so that
W6-A2's spread of about 12% across targets, darwin/arm64 the highest, and
the 15% between runs leave it within the ceiling. 500,000 peaked at 86%.
The change is in D3's table, §14.6 of chapter 14 and `internal/limits`.
`TestCalibrationLowered` needed no change: its `schema-work` cases run at
100,000.

What the lower default refuses:

- **A validation that costs more than 450,000 units**, which is now
  refused before it runs. `internal/schema`'s benchmark collection of
  10,000 items costs 350,001; an array of more than about 450,000 items
  costs more than that under any schema with `items`. A data limit admits
  more than one validation can see: `collection-items` (100,000) at more
  than four units an item, and `csv-rows` (1,000,000) at any schema that
  looks at each row.
- **The `sec/schema-work` vector's `exponential` case** lowered the limit
  to 1,000,000, which is now above the default and refused as a usage
  error. It lowers it to 400,000, and its expected bound follows.
- **`TestUniqueItemsMillion`** (ADR-009 D17 item 6's million items)
  shows the million refused by `schema-work`, and checks `uniqueItems`
  over the most items the default lets one validation see, 449,999. The
  `dat/unique-items` vector's note says so.
- **`TestBenchCollection` and `BenchmarkValidate`** compile a schema for
  each validation, since each is a command of its own, with its own
  `schema-work`.

**Proposals for Ed, after the train.** A3 item 5 lets `schema-work` rise
again on evidence of a lower cost per unit. Two changes could give that
evidence; neither is made here:

- **A bound on the findings nested in one alternative** would not help:
  after this item the listing is bounded by `findings`, and the
  `schema-work-anyof` case's peak is close to proportional to its units,
  with almost no constant part. The tree, not the listing, is the cost.
- **A soft memory limit for the collector** (`runtime/debug.SetMemoryLimit`)
  keeps the resident peak near the live heap. Under `GOMEMLIMIT=512MiB`,
  `anyOf 16` peaked at 721 MiB, not 1,022 MiB, at about twice the CPU. That
  is a runtime policy for ADR-010, measured on every target, before it
  could support a higher default.
- **The adapter's evaluation paths** could share their common prefixes
  rather than each failure holding its own, which is most of what the
  adapter holds per unit.

## Loading an input

**The mechanism.** A JSON input is read into the data model's value tree,
with a position tree beside it, then built again as `inputs`' assembly
tree, then once more as the inputs object validated, and canonicalized
through `gowebpki/jcs` for the input's digest, which parses the text into
a tree of its own. A YAML input is first parsed by `go.yaml.in/yaml/v3`
into its node tree. A CSV row is an object, built by `inputs`' reader.

| Input | Size | Values | main | C6 |
|---|---|---|---|---|
| JSON `[0,0,…]` | 2 MB | 1,000,001 | 504–521 MiB | 484 MiB |
| JSON `[0,0,…]` | 4 MB | 2,000,001 | 955–1,000 MiB | 963 MiB |
| YAML `- 0` lines | 1 MB | 250,001 | 185 MiB | 192 MiB |
| YAML `- 0` lines | 4 MB | 1,000,001 | 664–745 MiB | 784 MiB |
| CSV `0,0` rows | 1 MB | 250,000 rows | 676 MiB | 761 MiB |
| CSV `0,0` rows | 4 MB | 1,000,000 rows | 2,878 MiB | 2,768 MiB |

That is about 240 bytes of resident memory per byte of a JSON input, 190
per byte of YAML, and 700 per byte of CSV, or about 470 bytes per JSON
value and 2.8 KiB per CSV row of two fields. `go.yaml.in/yaml/v3`'s own
node tree for the 4 MB YAML input is 157 MiB live and 200 MiB resident in a
process that does nothing else: about 160 bytes per node, built before
this tool reads a value. At `input-size`, 32 MiB, a JSON input of
`[0,0,…]` holds 16,777,216 values and a CSV input 8,388,608 rows of
`0,0`; at `inputs-total`, 128 MiB, four times as many.

**No in-memory form fits these defaults.** A slice of the data model's
values costs 16 bytes per element before the element itself, so the
64 Mi values `inputs-total` allows in `[0,0,…]` cost 1 GiB in that slice
alone. A cheaper form lowers the cost per value; it cannot bring
`input-size` and `inputs-total` within 1 GiB. That needs a bound on what
is decoded, counted as it is decoded, or lower byte defaults, and YAML is
parsed by a library that builds its node tree before any count of this
tool's could stop it. Item 5 of the item's brief sent that choice to Ed,
who ruled it as Amendment A4 (design session
`01a159ac-1a15-7017-9a1d-9f99bef3ad55`). `input-size`, `inputs-total` and
`findings` are unchanged.

## Amendment A4: `input-values` and `yaml-size`

**What this item built.**

- `limits.Counter` counts one limit across every reading of a command.
  `inputs.Supply` holds one for `input-values`, and gives it to each
  reader, which counts as it decodes and stops at the value that passes
  the bound:
  - `jsonx` counts each value as it begins, its root included, for a JSON
    file, `--inputs-json` and `--set-json`;
  - `yamlx` counts each node as it converts it, and an empty document's
    null;
  - `csv.Read` counts the array, then each data record's object and each
    field but an unquoted empty one, as it reads the record;
  - `inputs` counts a text file and a `--set` value one each, a Markdown
    file its object (its frontmatter's root, when it has one) and `body`,
    and a collection its array.
- `yaml-size` is checked on a YAML file's or collection item's bytes before
  anything else is done with it.
- Statements MTS-SEC-059 and MTS-SEC-060 in chapter 14, and vectors
  `sec/input-values` (each form's count, passing at it and refused one
  value under it) and `sec/yaml-size` (a document, one that does not parse,
  and a collection item, each refused a byte under its size). The rows
  are in §14.4, the chapter's data limits, beside `inputs-total`.
- `csv-rows` keeps 1,000,000, and D3 says that `input-values` binds first.

**The memory per value, cut first** (A4 item 3), with no value, finding
or position changed:

- an input's digest is written into its hash a piece at a time, by
  `jsonx.CanonicalDigest`, where it was the canonical text built whole and
  parsed again by `gowebpki/jcs`;
- a CSV's positions are one flat list of a line and a column for each
  field, not a map for each row;
- a YAML document's places hold a sequence's elements by index and each
  position in two 32-bit words;
- a plain text value shares its file's raw form, now held as a string,
  rather than copying it.

At 1,000,000 values on this host (two runs each):

| Shape | Before | After |
|---|---|---|
| JSON `[0,0,…]` | 460–521 MiB | 298–329 MiB |
| JSON `[{},{},…]` | — | 478–502 MiB |
| YAML `- 0` lines | 664–745 MiB | 417–577 MiB |
| YAML `[0,0,…]` | — | 427–492 MiB |
| CSV `0,0` rows (1,500,001 values) | 1,034–1,107 MiB | 639 MiB |
| CSV `0` rows | — | 502–520 MiB |
| 128 MiB of plain text | 753 MiB | 316–348 MiB |

The costliest shapes per value are an array of empty objects in JSON, a
flow sequence of zeros in YAML, and rows of one present field in CSV.

**`yaml-size` is 1 MiB**, the largest power-of-two MiB whose case alone, a
flow sequence of zeros, peaks within 40% of 1 GiB (410 MiB):

| `yaml-size` | Peak, three runs |
|---|---|
| 1 MiB | 215 to 306 MiB |
| 2 MiB | 495 to 601 MiB |
| 4 MiB | 776 to 785 MiB |

**`input-values` is 1,000,000**, the largest round value whose joint cases
peak within 80% of 1 GiB (819 MiB). Each joint case puts its format's
costliest shape at the values the rest leaves, the rest of `inputs-total`
as plain text files of `input-size` at most, and a last YAML document at
`yaml-size`:

| `input-values` | JSON | CSV | YAML |
|---|---|---|---|
| 1,000,000, four runs | 697 to 784 MiB | 760 to 806 MiB | 763 to 815 MiB |
| 1,100,000 | 809 MiB | 882 MiB | 807 MiB |

Each loading case's validation is then refused by `schema-work`, since
1,000,000 values pass its 450,000 units. It is judged on the loading.
`input-values` binds `csv-rows` first: a CSV of 1,000,000 rows holds at
least 2,000,001 values.

## The calibration cases

Six cases are added to `TestCalibration` and `TestCalibrationLowered`:

- **`findings-nested`**: one `anyOf` of branches of 16 failing `const`s
  each, sharing one subschema by `$ref`, whose alternatives list more
  than `findings`, cut short at the limit.
- **`schema-work-anyof`**: two-branch `anyOf`s nested by `$ref` over a
  type every level fails, of exactly `schema-work` units, accepted at the
  limit with its findings and refused one unit under it. Its units are a
  sum of levels of 4 × 2ʲ − 2 each, on a base of 4.
- **`yaml-size`**: one YAML document of exactly `yaml-size` bytes, a flow
  sequence of zeros, read, and refused a byte under it.
- **`input-values-json`, `-csv` and `-yaml`**: A4 item 3's joint cases,
  exactly `input-values` values, refused one value under it.

`findings-nested`'s lowered form fails against main, which lists 1,009
findings at a cap of 1,000; the loading cases' lowered forms name limits
main does not have.
